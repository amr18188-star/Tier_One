# دليل اختبار منظومة Tier 1

دليل لمن سيختبر المنظومة يدويًا: ما هي، ومن يستخدمها، وكيف تشغّلها، وما الذي يحدث فيها خطوة بخطوة، ثم حالات الاختبار جاهزة للتنفيذ.

---

## 1. المنظومة في دقيقتين

**منظومة Tier 1 لجامعة العاصمة** تتابع الأداء الاستراتيجي للجامعة. الفكرة:

1. للجامعة **خطة استراتيجية** من **6 ركائز** و**12 معيارًا** و**92 مؤشرًا** (كل مؤشر له تعريف ووحدة قياس ومصدر بيانات وقاعدة تجميع).
2. لكل مؤشر **مستهدف لكل سنة** من 2027 إلى 2031 (سنة الأساس 2026، أي 5 سنوات و20 ربعًا).
3. كل **ربع** تفتح الجامعة **دورة جمع بيانات**، فيصير لكل كلية وقسم وإدارة مركزية **نموذج** فيه المؤشرات المكلفة بها.
4. **مدخل البيانات** يكتب القيم ويرفق الأدلة (ملفات PDF) ويرسل النموذج.
5. النموذج يمر على **سلسلة اعتماد** (فصل مهام: من أدخل لا يراجع): ممثل القسم ← لجنة الكلية ← العميد ← لجنة Tier 1 بالجامعة.
6. بعد الاعتماد، **لجنة Tier 1 بالجامعة** نفسها تراجع كل مؤشر (قيمة كل كلية وقيمة الجامعة المحسوبة) وتنقل القيمة إلى **مؤشر الجامعة**.
7. من القيم المنقولة تُحسب **بطاقة الأداء**: درجة كل مؤشر ومعيار وركيزة، ثم **الدرجة الكلية والفئة** (1 إلى 5)، ويُصدَّر **ملف المجلس KPI.xlsx**.
8. كل عملية في المنظومة تُسجَّل في **سجلات مختومة** (من فعل ماذا ومتى وبأي قيمة قبل وبعد).

### الفلو الكامل (من الفتح إلى بطاقة الأداء)

```
مدير متابعة الخطة (planner)
  └─ ينشئ دورة ربعية ويفتحها
        └─ تنشأ نماذج: لكل كلية / قسم / جهة مركزية / الجامعة
              │
   مدخل البيانات  ── يدخل القيم + الأدلة ──► يرسل النموذج
              │
   (نموذج القسم) ممثل القسم ──► لجنة الكلية ──► العميد ──► لجنة Tier 1 بالجامعة ──► معتمد ✔
              │            ▲ في أي خطوة: «إعادة» بملاحظة ← يصحح المدخل ويرسل من جديد
              │
   لجنة Tier 1 بالجامعة (tier1) ── تعتمد نهائيًا، ثم تراجع كل مؤشر وتنقل القيمة إلى مؤشر الجامعة
              │
   بطاقة الأداء والتصنيف ◄── الدرجة والفئة وملف المجلس KPI.xlsx
              │
   مدير متابعة الخطة ── يغلق الدورة بسبب مكتوب
```

وبجانبه فلوان آخران:

- **القاموس:** إنشاء المؤشر ← استكمال تعريفه ← إرساله ← **اللجنة العليا** تعتمده برقم المحضر. تعديل المعتمد ينشئ **إصدارًا جديدًا** والمعتمد القديم يبقى ساريًا.
- **المستهدفات:** العميد أو لجنة الكلية يقترح مستهدف كليته ← **اللجنة العليا** تعتمده برقم المحضر.

## 2. الأدوار: عندنا 15 دورًا

| الرمز | الدور | ما يفعله باختصار |
|---|---|---|
| `SA` | المدير الأعلى | كل الإمكانيات دائمًا ولا تُعدَّل من المصفوفة |
| `PRES` | رئيس الجامعة | اطلاع شامل على كل شيء، ويدير الأدوار والإعدادات، بلا إدخال ولا اعتماد بيانات |
| `VP` | نائب رئيس الجامعة | يتابع الجهات التابعة لنطاقه (كليات محددة) |
| `HC` | عضو اللجنة العليا | **يعتمد** تعريفات المؤشرات والمستهدفات ويحسم التعارضات برقم المحضر |
| `PM` | مدير متابعة الخطة | يدير القاموس والمستهدفات والجهات والهياكل والدورات، ويجهّز التعارضات |
| `QA` | الجودة المركزية | يراجع التعريفات ومصادرها والتعارضات، ويطلع على كل الجهات. لا يعتمد النماذج |
| `T1O` | لجنة Tier 1 بالجامعة | **آخر خطوة اعتماد** في نماذج الجهات، ثم تراجع مؤشرات الكليات وتنقل القيم إلى مؤشرات الجامعة |
| `DEAN` | عميد الكلية | يتابع كليته ومستهدفاتها وهيكلها، وخطوة اعتماد في النموذج |
| `CTC` | لجنة Tier 1 بالكلية | يحدّث هيكل الكلية ومستهدفاتها، وخطوة اعتماد (لجنة الكلية) |
| `DREP` | ممثل Tier 1 بالقسم | يراجع بيانات قسمه قبل رفعها |
| `DE` | مدخل البيانات | يدخل قيم جهته ويرفق الأدلة ويرسل النموذج |
| `INIT` | مسؤول المبادرة | تحديث أنشطة المبادرة (مرحلة ثانية؛ **لا يوجد له حساب تجريبي**) |
| `VIEW` | مستخدم الاطلاع | يشاهد نطاقه دون تعديل |
| `SYS` | مسؤول النظام | الحسابات والإعدادات التقنية؛ **لا يرى محتوى المعاملات ولا يعتمد** |
| `AUD` | المراجع الرقابي | قراءة السجلات والتقارير والتصدير، بلا أي تعديل |

**النطاق:** كل دور له نطاق: الجامعة كلها، أو جهات محددة (كلية، قسم). مستخدم الكلية لا يرى إلا كليته وأقسامها.

## 4. التشغيل

```bash
docker compose -p tier1-dev -f docker-compose.dev.yml up
```

| ماذا | العنوان |
|---|---|
| **الواجهة (استخدمها للاختبار)** | http://localhost:5188 |
| الـ API | http://localhost:5150 |
| قاعدة البيانات PostgreSQL | `127.0.0.1:5440` (`tier1_dev` / `tier1_dev`) |

- أول تشغيل يحمّل الهيكل الرسمي. البيانات التجريبية اختيارية: شغّل `up` مع `--profile demo` فتحمّلها حاوية `tier1-dev-demo-data` عبر الخادم (نحو 35 ثانية بعد أن يجيب). سجلها يقول `Demo data loaded in ... seconds` ثم تنتهي: `docker logs tier1-dev-demo-data`.
- **لإعادة كل شيء من الصفر:** `docker compose -p tier1-dev -f docker-compose.dev.yml down -v` ثم `up` (مع `--profile demo` إن أردت البيانات التجريبية).
- **الرسائل (البريد):** لا خادم بريد في التطوير؛ كل رسالة تُكتب ملف `.eml` في `data/mail`.
- **ملاحظة:** سجّل الدخول بحساب واحد في كل متصفح. لاختبار حسابين معًا استخدم نافذتين: عادية وخاصة (Incognito).
- **اختبارات آلية** (تغطي معظم ما في هذا الدليل): `dotnet test tests/Tier1.E2E` والخادم يعمل.

## 5. حالات الاختبار

كل حالة: **الحساب** ← **الخطوات** ← **المتوقع**. القائمة الجانبية تتغير بحسب الدور، وتبقى الأسماء بالعربية كما في الواجهة.

### أ. الدخول والجلسة

| # | الحساب | الخطوات | المتوقع |
|---|---|---|---|
| A1 | `planner` | ادخل بالبريد وكلمة المرور الصحيحة | تفتح «الرئيسية» وتظهر قائمة المتابعة «مطلوب منك» |
| A2 | أي حساب | اكتب كلمة مرور خاطئة | رسالة خطأ، ولا دخول |
| A3 | `viewer` | أخطئ **5 مرات** متتالية | يُقفل الحساب **15 دقيقة** ولو كانت المحاولة السادسة صحيحة. بعد ذلك يعمل |
| A4 | `planner` | سجّل الخروج ثم افتح رابطًا داخليًا (مثل `/cycles`) | تعود إلى صفحة الدخول |
| A5 | أي حساب | اكتب بريدًا غير موجود | الرسالة نفسها لخطأ كلمة المرور (لا تكشف وجود الحساب) |
| A6 | أي حساب | بعد 30 دقيقة خمول | تنتهي الجلسة ويطلب الدخول من جديد |
| A7 | `planner` | افتح الدخول في نافذتين لنفس الحساب | كلتاهما تعمل (جلسات متعددة مسموحة) |

## 8. ترتيب مقترح للاختبار

1. **الدخول والصلاحيات** (أ، ب) بحسابات كثيرة: أسرع طريقة لكشف أخطاء النطاق.
2. **القاموس والمستهدفات والخطة** (ج، د، هـ).
3. **الجهات والهياكل** (و، ز).
4. **دورة كاملة**: أنشئ دورة تجريبية (ح) ← أدخل (ط) ← اعتمد (ي) ← استورد (ك) ← راجع وانقل (ل) ← النتائج والبطاقة (م) ← أغلق.
5. **الإدارة والسجلات** (ن، س) في الآخر، لتجد أثر كل ما فعلته مسجلًا.

> بعد الاختبار: لتنظيف ما أضفته أعد القاعدة بـ `down -v` ثم `up`.
