**الصورة العامة:** الأساس متين. الطبقات سليمة الاتجاه (Application لا تعتمد على Infrastructure، وDomain بلا حزم)، وكل مسار يعلن صلاحيته مع سياسة احتياطية، والجلسات خادمية ومدوّرة. وفي المنظومة أيضًا:
- CSRF على كل طلب يغير الحالة، وكلمات المرور بـ PBKDF2 بـ 210 ألف تكرار، وTOTP يمنع إعادة الاستخدام.
- سجل تدقيق بسلسلة تجزئة عبر outbox في المعاملة نفسها، ورموز إصدار على معظم الجداول، وقيود تفرد لمعظم القواعد.
- واجهة بمسارات محملة عند الطلب، وحالات تحميل وخطأ موحدة، وRTL منطقي في الغالب.

**الفجوات الكبرى:**
- نطاق الاعتماد غير مربوط بنطاق الدور.
- لا CI ولا اختبارات تكامل للخدمات.
- الإشعارات بريد فقط وغير جاهزة لقنوات أخرى.
- أداء الإشعارات والصفحة الرئيسية لا يتحمل نمو البيانات.
- بعض قواعد الأعمال تنتظر قرارًا من مالك المنتج.

## 4. أهم الملاحظات المفتوحة حسب المحور

مرتبة بالخطورة. التفاصيل والإصلاح المقترح في التقرير المفصل لكل محور.

### منطق الأعمال والمتطلبات
- عالٍ: D1 إلى D5 أعلاه.
- متوسط: BL-9 (فحص الفصل بين المهام لا يشمل المرسل ومن عدّل قبله)، وBL-12 (البذرة تضيف صلاحيات الاعتماد المباشر للأدوار القائمة بلا تدقيق ولا اعتماد ثانٍ)، وBL-13 (الدورة تفتح بمؤشرات عليها تعارضات غير محسومة)، وBL-14 (رسائل المراجعة تصل لكل معتمد محتمل، ومنهم المديران الأعليان).
- مراجعة الكود: CR-4 (بعد إعادة النموذج وإرساله ثانية يختفي من «بانتظاري» عند من اعتمده في الجولة السابقة)، وCR-8 (استيراد Excel يتجاهل تغيير السبب وحده، ويقرأ «1,5» على أنها 15)، وCR-9 (العرض الافتراضي للنتائج قد يفتح دورة تجريبية).

### الأمان (لا ملاحظات حرجة)
- متوسط:
  - SEC-1: قنبلة zip في استيراد Excel؛ يفحص الحجم المضغوط فقط، فيستطيع أي مدخل بيانات إسقاط الخادم.
  - SEC-2: إنشاء الجهات وتعديلها وإسناد المؤشرات بلا فحص نطاق، وهي ثغرة كامنة.
  - SEC-3: توزيع المستهدفات يعيد مستهدفات كل الكليات لمن يرى وحدته فقط. **أُصلح** (فرع `college-targets-view`): الكلية ترى صفها وإجمالي التوزيع فقط، وأضيفت حصتها من مستهدف الجامعة في مؤشرات الأعداد.
  - SEC-4: الإنتاج يتصل بـ PostgreSQL بالمستخدم الأعلى.
  - SEC-7: إسناد الأدوار لا يطبق قاعدة «لا تمنح ما لا تملك».
  - SEC-8: لا حصة لرفع الملفات.
- منخفض: SEC-9 إلى SEC-16 (أعداد التعارضات في الصفحة الرئيسية، وقفل الحسابات، وتحصين Docker، وفحص الاعتماديات والأسرار في CI).
- `npm audit` للحزم الإنتاجية: 0 ثغرات. فحص حزم NuGet (`dotnet list package --vulnerable`) لم يشغّل بعد.

### الخادم وعقود API والتكامل
- عالٍ:
  - BE-2: رمز الإصدار الفارغ يتخطى فحص التزامن، فيكتب الحفظ فوق تعديل غيره دون تنبيه. والإرسال والإعادة وإعادة الفتح بلا إصدار أصلًا.
  - BE-4: `CyclesService.UpdateAsync` و`UnitIndicatorsService.SaveAsync` يحفظان تحديثًا جماعيًا قبل الحفظ الرئيسي، فيبقى التحديث بلا تدقيق إن فشل الثاني.
- متوسط:
  - BE-6: عقد الأخطاء غير موحد، وأخطاء الربط في الإنتاج تعيد 400 بلا جسم.
  - BE-7: قيم enum غير معرفة تقبل وتخزن.
  - BE-8: لا idempotency للإنشاء والرفع، فالنقرة المزدوجة تكرر.
  - BE-9: `App:PublicUrl` يعود بصمت إلى localhost.
  - BE-10 وBE-11: الإشعارات بريد فقط بنص ثابت، ولا شاشة لإعادة إرسال الفاشل، وهو مطلب 4-15.
- العقود: نحو 35 DTO ونحو 100 مسار في الواجهة متطابقة اليوم، لكن الأنواع تكتب يدويًا بلا OpenAPI يكشف الانحراف (BE-22).

### قاعدة البيانات والأداء
- عالٍ:
  - PERF-B1: كل إرسال أو اعتماد يحسب صلاحيات كل المستخدمين واحدًا واحدًا داخل الطلب، أي آلاف الاستعلامات لكل اعتماد.
  - PERF-B2: الصفحة الرئيسية وقائمة النماذج تحملان كل نماذج كل الدورات وتفحصانها في الذاكرة بلا ترقيم.
  - PERF-B3: صفحات الاتجاه وتقدم الكليات تعيد بناء نتائج كل دورة، ولا تخزن نتائج الدورات المغلقة.
- متوسط:
  - DB-3: «دورة رسمية واحدة لكل عام وربع» بلا قيد في القاعدة.
  - DB-4 وDB-5: حذف المستهدف يمحو تاريخه، والقيم الرسمية تكتب فوق نفسها بلا جدول تاريخ.
  - DB-6: أعمدة `university_values` بلا دقة عشرية ثابتة.

- **SSO عبر OIDC (البند 6):** يحتاج قرارًا (ADR-011 المقترح).
- **OpenTelemetry:** حزمه المتاحة محليًا قديمة، ولا مُجمّع قياسات في البيئة بعد. فحص الجاهزية يغطي التنبيه الأساسي حتى يحدد مكان القياسات.
- **أنواع TypeScript مولدة من OpenAPI:** نُفذت مقدمتها. المسارات تعيد `TypedResults.Ok`، فصار لـ105 من 135 مسارًا مخطط استجابة في العقد المعتمد (196 مخططًا)، واختبار العقد يكشف تغير شكل الاستجابة أيضًا. والباقي مسارات بلا محتوى أو ملفات. وأنواع الواجهة مولدة منه (`npm run gen:api`، بحزمة openapi-typescript بموافقتك) في `src/api/schema.d.ts`، و`src/api/contract.check.ts` يقارن 30 نوعًا تقرؤها الشاشات بما يرسله الخادم فيفشل فحص الأنواع عند أي انحراف، واختبار يفشل إن تأخر الملف المولد عن العقد. وكشفت المقارنة انحرافًا واحدًا صحح: سجل القيمة في المراجعة قد يأتي null.
- **بادئة `/api/v1`:** لا عميل خارجي اليوم، والواجهة تنشر مع الخادم. تضاف مع أول تكامل خارجي، فلا تختلط بادئتان في واجهة واحدة.

**الخطة الأصلية:**
هذه هي البنية التي تسمح بإضافة واتساب وSMS والدفع وSSO دون لمس منطق الأعمال. التصميم الكامل في [review-backend.md](review-backend.md) («Extension readiness and target design»).
1. **outbox عام لأحداث المجال** (`int.outbox_events`) بمعالجات idempotent (`int.processed_events`). الخدمات تضيف حدثًا قبل `SaveChanges` الوحيد، ولا تستدعي المرسلين مباشرة.
2. **خط إشعارات متعدد القنوات:**
   - قوالب لكل حدث وقناة ولغة (`notify.templates`).
   - تسليمات بحالة (`notify.deliveries`: معلق، مقبول، مسلَّم، فاشل قابل لإعادة المحاولة، فاشل نهائي).
   - صندوق داخل التطبيق (`notify.inbox`)، وهو مطلب 4-15.
   - شاشة إدارية لإعادة إرسال الفاشل.
3. **محولات المزودين** في `Infrastructure/Integrations/<Provider>/`: إعدادات مُتحقق منها عند البدء، و`HttpClient` بمهلة وإعادة محاولة وقاطع دائرة، وواجهة `IChannelSender` موحدة. والمحولات المطلوبة:
   - SMTP (الحالي).
   - WhatsApp Cloud API: قوالب معتمدة، وموافقة المستخدم، ونافذة 24 ساعة.
   - SMS.
   - الدفع، إن احتيج.
4. **Webhooks الواردة:** تحقق من التوقيع على الجسم الخام، وجدول `inbound_events` لمنع التكرار وإعادة التشغيل.
5. **بيانات اتصال المستخدم:** هاتف بصيغة E.164، وموافقة واتساب، واللغة، والقناة المفضلة.
6. **SSO عبر OIDC** (Entra ID أو غيره) مربوط بالجلسات الخادمية الحالية، فيبقى الإبطال الفوري.
7. **المراقبة:** OpenTelemetry (قياسات وتتبع)، وفحص جاهزية يشمل Mongo وعمر outbox، وتنبيهات على التسليمات الفاشلة.
8. **العقد:** OpenAPI، وتوليد أنواع TypeScript منه، وفحص فرق في CI (BE-22)، وبادئة `/api/v1` للمسارات الجديدة.

2. المسار محمل عند الطلب، ومحمي بالصلاحية نفسها التي في الخادم.
3. قائمة التحقق في [review-ux.md](review-ux.md) («Extension readiness»):
   - صفحة أم نافذة أم درج.
   - حالات التحميل والفراغ والخطأ.
   - حراسة الإدخال غير المحفوظ.
   - تسميات الحقول.
   - صفوف قابلة للوصول بلوحة المفاتيح.
   - رموز التصميم `--ds-*` لا ألوان خام.
   - CSS منطقي لـ RTL.
   - WCAG 2.2 AA.

## 7. قرارات معمارية مقترحة (ADR)

| ADR | القرار |
|---|---|
| 001 | Monolith معياري على Postgres، بمخططات ومنافذ لكل وحدة، واختبارات معمارية تفرض الحدود |
| 002 | عقد الأخطاء: RFC 9457 (`problem+json`) مع `code` و`traceId` و`errors[]` |
| 003 | التزامن: رمز إصدار إلزامي في كل تعديل وانتقال، ولا لمس للصف الأب بتعديل الأبناء |
| 004 | `Idempotency-Key` للإنشاء والرفع والقرارات |
| 005 | outbox عام للأحداث ومعالجات idempotent؛ الإشعارات بعد الحفظ دائمًا وغير متزامنة |
| 006 | نموذج الإشعارات: القنوات، والقوالب، وبيانات الاتصال والموافقة، والصندوق الداخلي |
| 007 | معيار محولات التكامل: الإعدادات، والمرونة، والتحقق من webhooks، وتدوير الأسرار |
| 008 | المهام المجدولة: قائد واحد عبر advisory lock عند تعدد النسخ |
| 009 | إصدار API (`/api/v1`) وOpenAPI مصدرًا لأنواع الواجهة |
| 010 | الصحة والمراقبة: OpenTelemetry وتنبيهات |
| 011 | SSO عبر OIDC (يحتاج قرارًا) |
| 012 | الاحتفاظ بالبيانات لجداول outbox والبريد والملفات |

**أسئلة مفتوحة:**
- هل يعمل الخادم بأكثر من نسخة؟
- أي مزود للواتساب والـ SMS، وهل اعتمد حساب WhatsApp Business؟
- هل SSO الجامعة ضمن المرحلة الثانية؟
- ما مدة الاحتفاظ بمحتوى الإشعارات؟
